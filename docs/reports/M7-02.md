## Operational limits and owner gate

- The app must be running and healthy. Sleep/off time is handled by one latest-slot
  catch-up; it cannot create the missing historical backups. API/worker must use the
  same stable BACKUP_DIR and target. A new empty directory starts a new history.
- Windows kernel lock tests ran on this laptop; the POSIX fallback is not exercised
  here. Lock behavior follows the [Python msvcrt documentation](https://docs.python.org/3.12/library/msvcrt.html).
- A hard crash inside the M7-01 dump may leave `.lock` and an orphan subprocess.
  Never automatically remove it. The UI asks for engineer inspection; bounded retries
  and the next schedule remain safe. Crash after publication reconciles success even
  if retention was not reached. Retention errors retry after the next successful copy.
- Corrupt journal/archive requires inspection; deleting schedule.json to clear a
  warning can lose deduplication history. Interrupted private `.tmp`/`.partial` files
  are not valid archives and are not automatically removed by this task.
- Status records the verified archive's creation timestamp. No costly continuous
  checksum scan is implied by a green status. A stopped worker is detected after
  2 minutes, or 35 minutes if its last state was running a potentially slow dump.
- Local disk/fsync/rename do not guarantee survival of physical disk failure or every
  sudden-power-loss filesystem outcome. Retain the M7-01 off-device responsibility.
- Automated tests use synthetic archives/clocks; no claim that this laptop actually
  crossed 18:00 or performed a real startup catch-up during engineering validation.
