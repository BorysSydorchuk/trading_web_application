## Change and reproducibility

Added opt-in developer tools, synthetic data and deterministic safety/statistics tests.
No production application, money/risk math, schema, MT5 adapter, dependency or UI changes.
RED checkpoint `a8884c6`; additional threshold-count test observed RED then GREEN.
The benchmark reports every threshold breach as well as median, nearest-rank p95,
maximum and raw samples. A successful tool exit means measurements completed;
`failures` in its JSON is the performance verdict, independent of correctness tests.
PRD §7 requires startup <10 s and local pages <300 ms; the PM also requires API <300 ms.
These strict limits are not relaxed to p95: even one slower sample is disclosed.

From ordinary Windows PowerShell at the repository root, with existing dependencies,
healthy local PostgreSQL, Chrome installed, and application settings configured by owner:

```powershell
uv run --project backend python -m app.tools.performance --phase baseline --repetitions 20 --startup-repetitions 10
python scripts/performance_environment.py --repetitions 3
```

The first command creates its own random local `_test` database, temporary config,
data/log/backup folders, ports and Chrome profile. It refuses an existing generated
database or a nonlocal/non-generated target; fixed dev/QA names cannot be benchmark
targets. It uses the existing local test connection only to create the new database.
The generated DB is migrated from empty; no existing DB is migrated, reset or deleted.
The fixture worker has synthetic accounts without terminal paths, empty audio queues
and a blank AI key. There are no real MT5, AI or Whisper calls. Workers may perform
normal maintenance and scheduled backup work only on the synthetic target.
The tool stops only its own child trees; retained DBs/temp folders are deliberate.
Do not run concurrently with the full test gate or other measurements.

The second command creates three new PostgreSQL containers with fresh PGDATA using
the already cached immutable PostgreSQL 16 image, binds random loopback ports, waits
for healthy status, then stops only each exact new container ID. Stopped containers,
volumes and fresh dependency installations are retained. It does not stop Docker,
the application's container or any existing database. Fresh installs copy tracked
backend/frontend/config files, exclude secret files, use empty venv/node_modules,
warm offline uv/npm caches, and run the frontend build. No application/model is run.

## Measurement definitions

- API: real TCP HTTP via loopback, serial keepalive requests, complete body and JSON
  decoding, one excluded prime per endpoint, 20 measured repetitions. Includes
  filtered/paginated journal (50/200), dashboard supporting endpoints, saved digest
  detail/list/suggestion/generation, specs and offline calculator. No AI generation
  or terminal margin requests. API response time is separate from browser time.
- Browser: native Node CDP and private headless Chrome, viewport 1440×1000, DPR 1,
  external HTTPS blocked. One excluded prime/page then 20 measured document loads
  with warm assets and fresh React state. Timing ends after required Ukrainian title,
  real dashboard/select/table content, no pending API fetches, and two animation
  frames. Separate 20 actual sidebar navigations/page with warm React Query cache
  follow one excluded navigation round. These are usable-page checks, not visual
  screenshot/LCP/interaction-completeness certification.
- Startup: PostgreSQL, dependencies and Chrome already running/warm; no pending
  migration or dependency install. One first start with cold browser assets reported
  separately, then 10 repeated child restarts. Includes dependency/version/stamp
  checks, web startup overlapping DB/preflight/migration, normal `uv run` API and
  worker startup/readiness and usable Home. Reuses launcher functions; API alone has
  a benchmark clock override to 2026-11-13T17:00:00Z. Checks cannot recover/stop an
  owner's process. Excludes launcher CLI boot/import, reading secret-file/old-run
  recovery, opening a new interactive browser and cold Docker/install. Owner timing
  is therefore still required for complete `start.bat` experience.

All 340 final API samples were <300 ms (largest 108.467 ms). **Performance verdict:
partial FAIL, `browser:/journal`**; correctness gate success cannot erase this.
Startup passed the final series; preliminary intermittent startup tails below are
still an unconfirmed risk, not proof of a production improvement.

Journal investigation: the two breaches were 329.1/335.0 ms, not a failed API or
network document load (HTML response end 3.2/4.2 ms, DOMContentLoaded 50.8/50.6 ms).
During these page loads the slowest fetch callback completed in 170.2/208.2 ms;
direct serial journal API p95 was only 12.082 ms. Browser callbacks include main
thread contention and concurrent requests, so they are not interchangeable with
the serial API measurement. Sidebar journal p95 82.1 ms confirms the cached path
is substantially cheaper. Root cause within parallel fetch/render work is not yet
proven. Minimal proposal [M]: profile the 50-row table render and concurrent initial
fetches; cache repeated display formatting or memoize unchanged rows only if the
profile identifies that cost, with Ukrainian display/interaction regression tests
and the same before/after workload. No speculative UI/SQL/financial fix is included.
PM disposition is required for the failed target; no claim of full PRD compliance.

Preliminary baseline (earlier harness, worker launched directly): five warm starts,
median 7,632.711 ms, p95/max 12,654.417 ms, one breach. API p95 5–53 ms;
document page p95 190–280 ms. Expanded preliminary diagnostic: ten warm starts,
median 7,816.155 ms, p95/max 12,466.774 ms, one breach. Both sets are retained
under `logs/m7-05-{baseline,diagnostic}-tj_m705_*.json` and are not pooled with the
final launcher-aligned measurement.

Stage timings localized the extra ~5 s to child readiness (9,222 ms vs usual
4,306–4,636 ms), before the API's first startup log; preflight/migration and usable
Home did not explain it. Worker risk recomputation was ~2.4 s in ordinary starts,
but this does not establish it as the cause of the outlier. Twenty isolated API
import probes (10 uv, 10 direct interpreter) did not reproduce the delay: uv
1,897–1,953 ms vs direct 1,849–1,948 ms. Replacing uv on this evidence would be
speculative and saves only ~44 ms on average, so it was not implemented.

Minimal follow-up proposal [M]: capture process creation-to-first-log and individual
readiness probe durations on a reproduced owner slow start, then remove a proven
wait/import bottleneck with its own correctness regression and comparable after run.
Do not bypass health checks, change readiness semantics or move risk recomputation
merely to improve the reported number. Any deferred/incremental risk recomputation,
money calculation, schema/index migration or MT5 change needs separate PM approval
and Tier L reassessment. There is no such change in this task.
